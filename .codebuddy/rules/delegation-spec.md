# 仓库发配规范（Delegation Spec）

本规范约束 AI 在本仓库内的子代理发配、验收与来回用词。用户级技能（如 delegate-or-not）提供默认协议；本规范是仓库的最终事实源，两者冲突时以本规范为准。

## 分支与提交约定

- 提交一律由主线程执行；子代理只修改工作树，**禁止子代理执行 git commit/push**。
- 子代理产出提交信息：`[delegate:<task>] <摘要>`；主线程直接修改：`[main] <摘要>`。
- 隔离分支名：`delegate/<task>`；worktree 目录：`../wt-<task>`。

## 发配四步（每步以完成标准收尾）

1. **锁基线**：`git status --porcelain` 输出为空；记录 `git rev-parse HEAD` 的 SHA。
   完成标准：工作树干净，基线 SHA 已写入发配记录。
2. **发配**：提示词含四段——背景、目标、边界（白名单路径清单）、产出格式；**改代码类发配必须附《设计意图说明》**（当前版本见仓库根 AGENTS.md「设计意图」节），冲突即停手上报。
   完成标准：白名单与产出格式已逐字写入提示词。
3. **验收**：`git diff --stat` 对照白名单，逐项三查（越界、夹带、破坏）。
   完成标准：diff 全部落在白名单内，改动均有清单依据。
4. **归档**：通过则按提交约定由主线程提交；不通过则 `git restore .` 回滚到基线 SHA。
   完成标准：提交或回滚二选一已发生，工作树回到干净态。

大任务或并行发配改用 worktree：`git worktree add ../wt-<task> -b delegate/<task>`，验收 `git diff main...delegate/<task>`，通过 `git merge`，不通过删分支即可。

## 验证命令（验收第 3 步）

- **用户已授权 AI 执行 gradlew 构建验证**（2026-09-06 起）：
  - 编译检查：`gradlew :app:compileDebugJavaWithJavac`
  - 安装包构建：`gradlew :app:assembleDebug`（产物 app/build/outputs/apk/debug/）
- 验收手段：`git diff` 审查 + 构建验证 + 逐项对照修复清单。

## 报告用词（反引导协议）

- 每份来回报告按 `事实与证据 → 结论（含负面清单）→ 未决问题` 组织；结论锚定文件:行号、命令输出或 diff。
- "无问题"必须附验证手段（跑了什么命令、看了什么 diff）。
- 状态由验收产生：diff 审查通过才算完成，叙述措辞不产生状态。
- 禁止无证据评价性形容词（顺利/显著/基本完成/质量不错）；禁止预期式结论（应该没问题/理论上已修复）。

## 任务书格式（防泄露）

- 任务书只含确定性指令：背景、逐项指令（问题/位置/修法/验收标准）、勿动清单、完成标志。
- **禁止**出现：审核轮次与分级痕迹（如"MAJOR"/"PARTIAL→修"/"第 N 轮发现"）、执行者指派、裁决过程字样（"已裁决"/"倾向"/"二选一"）、过程统计（复现率等）。
- 括号仅允许用于技术参数与形态说明；流程信息一律留在主线程。

## 并行修改类发配（实测约束，2026-09-20 追加）

一次实测：4 个 `[模式:修改]` 子代理按互不重叠的文件白名单并行，共 26 个文件。
结果：**2 个批次破坏编译（共 5 处），自检命中 0 处** —— 全部由主线程统一构建抓出；其中一个批次
**未执行**给定的裁决口径，另一个批次**无视**禁令破坏了跨文件契约。据此追加五条：

1. **构建由主线程独家执行，且在并行批次里不可省。**
   不要让并行子代理各自构建（会争抢 Gradle 锁）；提示词写明「禁止运行构建」，全部回报后由主线程跑一次全量构建。
   这是这类批次唯一有效的闸门 —— 实测那 5 处破坏只有构建能抓出。
   **代价须知**：禁用构建等于移除了子代理唯一的自检手段，故主线程这一步必须真的执行，不能用「读 diff」代替。
2. **只写「不要动白名单外的文件」是无效禁令。**
   实测：提示词明确写了「若需动 `HomeListState.kt` 就不要动、写进未决问题段」，子代理仍删掉了它所依赖的构造参数 ——
   断链后既没改对、也未上报。有效做法二选一：把契约的**生产者与消费者一起**纳入白名单；
   或点名列出「改了它会波及哪些文件」并要求「命中此情形立即停手上报」。
3. **裁决口径会被部分执行，验收必须逐条比对裁决项。**
   实测：一条裁决写明「去掉页面级水平内缩 + 三处非组件内容各补同一 token」，实际只补了一处、页面级没去 ——
   原问题未修，还新增一处错位。验收时对照原裁决**逐项打勾**，不能只看「这个文件有没有被改」。
4. **报告丢失 ≠ 验收通过；验收标准必须逐条回执。**
   实测：批次自述报告在中断中丢失，主线程改用「读 diff」代替「证明验收标准」，
   导致三条已写下的等价性标准**从未被证明**却被当成已通过。
   规则：报告没到就重新索取，或由主线程机械复现该验证；做不到就把该条明确标为「未验证」，**不得默认成立**。
5. **等价类改动（提取 / 重构）的验收方式是脚本比对，不是人眼审 diff。**
   逐项比对旧实现与新实现的表达式 / 字段 / 参数映射，且断言两侧**无增无减**。
   配套硬约束：校验器必须自带「样本数非 0 且符合预期量级」的自证断言 ——
   实测出现过解析错目标、在**空集**上打印「逐项一致」的情形；比对要取**完整表达式**，
   不能比前缀（一次 `head -c N` 截断曾让两段逐字相同的代码被判为「不同」）。

## 当前生效的管理规定

- **子代理指派**：**只读**任务用只读探索型子代理（code-explorer / Explore）；
  **修改类**任务必须用**具备写工具**的子代理类型 —— 实测 `Explore` 类型**没有** Write/Edit 工具，
  用它做修改类发配会退化成「用 shell 写文件」，不可接受。禁止设置为 auto。
  （本条为 2026-09-20 实测修正：原表述「一律用 code-explorer」在修改类任务上不成立。）
